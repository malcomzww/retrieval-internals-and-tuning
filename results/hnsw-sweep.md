Recall in this file is **exact and portable**: it is measured against an
exhaustive scan of the same vectors, so every value below reproduces on
any machine. Latency is deliberately *not* here -- it is a wall-clock
measurement and belongs in `hnsw-sweep-raw.md`, which is gitignored.
What is committed instead is the *ordering* of configurations by cost,
which is the part that survives a change of hardware.

to change per query. That asymmetry is the single most useful fact about
tuning HNSW, and it is why the table is organised this way: pick a row
once, move along it as much as you like.

Asserted by this script, and it exits non-zero if any of these break:

- Recall is **monotone non-decreasing in `ef_search`** for every graph.
- Recall **strictly increases** from the lowest to the highest `ef_search`.
- The best configuration reaches recall > 0.99 (measured: 1.0000),

## 4. IVF-PQ: compression against recall

`m_sub` sub-quantisers at 8 bits each replace a 1,536-byte float32
vector with `m_sub` bytes. The two axes fail differently and the table
separates them: `nprobe` is a *search-time* knob and its loss is
recoverable, while the code width is fixed at build time and its loss
is permanent.

| bytes/vector | compression | nprobe=1 | nprobe=4 | nprobe=16 | nprobe=64 |
|---|---|---|---|---|---|
| 16 | 96x | 0.250 | 0.350 | 0.380 | 0.380 |
| 48 | 32x | 0.338 | 0.520 | 0.583 | 0.588 |
| 96 | 16x | 0.362 | 0.645 | 0.768 | 0.777 |

At 32x compression the best recall measured is 0.777 against
0.380 at 96x -- asserted here, because "compression costs
recall" is the claim, and a run where it stopped being true would
mean the quantiser was not doing anything.

Unlike HNSW, **no IVF-PQ configuration measured reaches recall 1.0.**
Quantisation discards information at build time; no search-time knob
recovers it. IVF-PQ is a memory decision that costs accuracy, not a
latency decision.
