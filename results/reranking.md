# Re-ranking: at what latency budget does it stop being worth it?

Generated by `python scripts/generate_results.py`. Do not edit by hand.

- Date: 2026-08-25
- Corpus: 20,000 synthetic passages, k=10, 60 queries
- Embedder: sentence-transformers/all-MiniLM-L6-v2
- Hardware: 24-core CPU, 32 GB RAM, no GPU (Windows AMD64, Python 3.13.5)
- Ground truth: exhaustive flat inner-product scan of the same vectors
- Seeds: corpus 0, queries 1, bootstrap 0
- Reproduce: `uv run python scripts/generate_results.py`

**The comparison this file makes.** The usual framing -- "ANN at ef=64"
versus "ANN at ef=64 plus a re-ranker" -- is not a fair fight: the second
arm is handed extra milliseconds the first was never offered. Here the
*total* per-query latency is what each arm is charged, so a budget spent
entirely on retrieval (a larger `ef_search`, or an exact scan) competes
against a budget split between cheap retrieval and re-ranking.

Quality is NDCG@10 against relevance labels derived from the corpus text
-- documents that genuinely discuss both concepts the query asks about --
**not** against the embedding's own ranking. Queries are paraphrased, so
a query asking about the "flush barrier" must match documents saying
"checkpoint". Both choices matter: an earlier version scored relevance by
the exact embedding ranking, every retrieval arm scored NDCG 1.0000 by
construction, and "re-ranking never pays" fell straight out of the setup.

## The answer: re-ranking never paid

**At no budget tested did a re-ranked arm beat the best retrieval-only
arm.** This is reported as measured rather than adjusted until a
crossover appeared.

## What holds on a different machine

- **Portable:** the NDCG and MRR of every arm (exact, no timing),
  the ordering of arms by cost, and the ~0x cost ratio
  between the cross-encoder and dense retrieval, which is set by
  transformer arithmetic rather than by this laptop.
- **Not portable:** the millisecond value of the crossover. A different
  CPU moves it; a **GPU moves it by one to two orders of magnitude** and
  can erase it entirely. On a GPU re-ranker the honest answer to this
  repo's question is likely "re-ranking pays at almost any budget", and
  nothing measured here contradicts that.

## Why the lexical re-ranker loses

BM25 over the candidate set costs almost nothing and does not help here
-- often it actively hurts. That is a consequence of the paraphrased
queries: when the query says "flush barrier" and the document says
"checkpoint", there are no shared terms for BM25 to score, so it reorders
the candidates close to arbitrarily. A lexical re-ranker needs lexical
overlap to exploit, and a genuine vocabulary gap is exactly the case
where dense retrieval is worth its cost and lexical re-ranking is not.
